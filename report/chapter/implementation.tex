\section{Implementation}
\label{sec:implementation}

\subsection{Domain-Specific Constraint Language}

\paragraph{Constraint representation.}

The domain-specific constraint language was designed to represent the constraints of the original ILP formulation as relationships between computations and buffers.
Rather than encoding these relationships directly as integer variables and linear inequalities, the language gives each kind of constraint an explicit constructor.
The language is implemented by the algebraic data type \texttt{Constraint}.
The following code listing shows two examples of constraints that express ordering relationships between computations.

\begin{lstlisting}[language=Haskell]
data Constraint
  = ClusterBefore (Node Comp) (Node Comp)
  | ClusterBeforeUnlessFused (Node Comp) (Node Comp)
  -- Further constraints omitted...
\end{lstlisting}

The order of the computation clusters is represented by integer variables $\pi_i$, where $\pi_i$ denotes the cluster index of the $i$-th computation.
Constraints on these indices ensure that the cluster ordering respects the dependencies between computations, with fused computations sharing the same cluster index.

The constraint \texttt{ClusterBefore} expresses the strict ordering $\pi_i < \pi_j$ between two computations $i$ and $j$.
For dependencies that permit fusion, the constraint \texttt{ClusterBeforeUnlessFused} requires $\pi_i = \pi_j$ if the computations are fused, and $\pi_i < \pi_j$ otherwise.
This constraint makes the relationship between fusion decisions and cluster ordering explicit in the constraint language.

\paragraph{Lowering to ILP.}

To keep support for the external ILP solver, the constraints are lowered into a linear representation.
For each constraint, lowering produces a tuple containing linear constraints, variable bounds and a contribution to the objective.
The lowering signature and its result type are shown in the code listing below:

\begin{lstlisting}[language=Haskell]
lower :: LowerEnv -> Constraint -> Lower

type Lower = State String (LinearConstraint, Bounds, Expression)
\end{lstlisting}

The \texttt{LowerEnv} parameter provides the total number of computations in the problem, which is used for some constraints to generate appropriate bounds and coefficients during lowering.
The \texttt{Lower} type uses a state monad to supply fresh variable names to introduce auxiliary variables when needed.
Some constraints may not produce additional bounds or objective contributions.

For example, the \texttt{HorizontalReadCost} constraint requires auxiliary variables to encode the cost associated with distinct clusters reading the same buffer.
Fresh names ensure that variables introduced for separate constraints do not collide.

As a simple example of the translation, \texttt{ClusterBefore} is lowered to
\[
   \pi_i < \pi_j.
\]

The lowering of \texttt{ClusterBeforeUnlessFused} additionally uses a binary variable $x_{ij}$, where $x_{ij} = 0$ means that computations $i$ and $j$ are fused, and $x_{ij} = 1$ means they are not fused.
The constraint is encoded as:
\[
    x_{ij} \leq \pi_j - \pi_i \leq M \cdot x_{ij},
\]
where $M$ is a sufficiently large constant determined by the total number of computations in the problem.

The function \texttt{lowerAll} lowers all constraints using a shared supply of fresh variable names and combines the results.

\subsection{Presolver}

The constraint language described above allows the problem to be simplified before it is lowered to an ILP.
The presolver uses a substitution to record known variable values and relationships between variables.
It uses this information to derive further assignments, drop already satisfied constraints, and detect contradictions.
These optimizations work directly on the domain-specific constraints, where relationships such as fusion and cluster ordering are still explicit.

\paragraph{Problem representation.}

The presolver represents a problem as a set of unresolved constraints and a substitution.
A substitution contains a mapping of variables to either a constant value or an alias to another variable.
Here is an excerpt of the main types:

\begin{lstlisting}[language=Haskell]
data Value = Const Int | Alias Var

newtype Substitution = Substitution (M.Map Var Value)

data Problem = Problem
  { constraints :: [Constraint]
  , substitution :: Substitution
  }
\end{lstlisting}

When a variable is looked up, the presolver follows the aliases until it resolves to a constant or a representative variable.
The substitution map uses an ordering of the variables to record aliases, which avoids cycles during lookups.

\paragraph{Constraint simplification.}

The main simplification function is:
\begin{lstlisting}[language=Haskell]
instantiate
    :: Substitution
    -> Constraint
    -> Either Infeasible (Maybe Constraint, [Assignment])
\end{lstlisting}

It simplifies a single constraint using the current substitution.
The result either contains the (simplified) constraint --- if it still needs to be enforced --- or omits it if it is already satisfied or represented by new assignments.
An assignment here is a pair of a variable and a value.
If the constraint contradicts the known assignments, it returns \texttt{Infeasible}.

For example, an \texttt{Unfused} constraint directly translates to an assignment of the fusion variable $x_{ij} = 1$.
If $x_{ij} = 0$, the \texttt{ClusterBeforeUnlessFused} constraint establishes $\pi_i = \pi_j$, which is recorded by aliasing the two cluster variables and dropping the constraint.
This also works the other way around: if the cluster variables are already equal, the fusion variable is fixed to $x_{ij} = 0$.
Conversely, if $x_{ij} = 1$, the cluster indices need to be different, which is represented by the emitted \texttt{ClusterBefore} constraint.

Similar rules are used in \texttt{instantiate} to simplify relationships like buffer materialisation, iteration directions, fold sizes, and in-place reuse.
All these rules can trigger further simplifications in other constraints.
This is handled by the \texttt{apply} function, which repeatedly simplifies the constraints until a fixpoint is reached.
This continues until the substitution no longer changes and the assignments in the substitution preserve the information from the dropped constraints.

\paragraph{Graph-based passes.}

The local simplification described above considers only one constraint at a time.
However, some optimization techniques are only possible if we consider multiple constraints together.
Therefore, the presolver also applies passes over the whole problem.
Every pass takes a problem instance and either returns a simplified problem or reports infeasibility.
The type of a pass is defined as follows:

\begin{lstlisting}[language=Haskell]
type Pass = Problem -> Either Infeasible Problem
\end{lstlisting}

The presolver defines several passes, some of which use a graph of the cluster ordering relationships to derive new information.
By default, four of them are enabled:

\begin{itemize}
    \item \texttt{noInPlace} finds buffers marked by \texttt{NoInPlace} constraints and disables the corresponding reuse paths represented by \texttt{InPlaceCluster} constraints.
    \item \texttt{piMaxOrder} derives ordering constraints from selected in-place reuse paths. If all candidate reuse paths associated with another read of the input buffer are disabled, that reader must precede the overwriting writer.
    \item \texttt{orderComponents} identifies strongly connected components in the ordering graph. It either sets the variables within a component equal by adding alias assignments or detects a contradictory cycle and reports infeasibility.
    \item \texttt{orderReachability} uses paths of strict ordering relationships to rule out fusion and in-place reuse choices that require equal cluster indices.
\end{itemize}

For example, \texttt{orderComponents} constructs a directed graph where the vertices are the cluster variables.
A \texttt{ClusterBefore} constraint contributes a strict ($<$) ordering edge.
In comparison, a \texttt{ClusterBeforeUnlessFused} constraint adds a non-strict ($\leq$) ordering edge.

Consider a cycle consisting of three non-strict ordering relationships:
\[
    \pi_i \leq \pi_j, \qquad
    \pi_j \leq \pi_k, \qquad
    \pi_k \leq \pi_i.
\]

Figure~\ref{fig:ordering-cycle} shows the corresponding ordering graph.
\begin{figure}[htbp]
    \centering
    \begin{tikzpicture}[>=stealth, every node/.style={font=\small}]
        \node[draw, circle, minimum size=9mm] (i) at (0, 0) {$\pi_i$};
        \node[draw, circle, minimum size=9mm] (j) at (4, 0) {$\pi_j$};
        \node[draw, circle, minimum size=9mm] (k) at (2, -2) {$\pi_k$};
        \draw[->] (i) -- node[above] {$\leq$} (j);
        \draw[->] (j) -- node[below right] {$\leq$} (k);
        \draw[->] (k) -- node[below left] {$\leq$} (i);
    \end{tikzpicture}
    \caption{A cycle of non-strict ordering relationships forces all three cluster indices to be equal.}
    \label{fig:ordering-cycle}
\end{figure}

Together, these relationships imply that the cluster indices are equal: $\pi_i = \pi_j = \pi_k$.
The pass records this by aliasing the variables in the substitution.
More generally, all variables of a strongly connected component containing only non-strict edges must be equal.
If such a component contains a strict edge, the ordering is contradictory.
For example, if the first relationship were strict ($\pi_i < \pi_j$), the cycle would require $\pi_i < \pi_i$, which is impossible.

The different passes are applied in sequence, followed by the local constraint simplifications.
This will be repeated until a fixpoint is reached, where these simplifications no longer change the problem.

\subsection{Custom Solver}
The custom solver is designed to use the domain-specific constraint language and the presolver to find an optimal solution to the problem, trying to achieve better performance than the external ILP solver by exploiting the structure of the problem.

\paragraph{Finding an initial solution.}

The solver starts by finding an initial feasible solution to provide a starting point for the optimization process.
Starting from the presolved problem, it uses a greedy algorithm to assign values to all the fusion choice variables.
For each candidate fusion variable, it tests both assignments, $0$ (fused) and $1$ (not fused), and checks if the assignment is still feasible using the presolver.
Every time a contradiction is found, the assignment is discarded.
The next variable to branch on is selected by a heuristic, which prefers the following in this order:

\begin{enumerate}
    \item Fewest feasible children.
    \item Fewest remaining fusion constraints, summed across all feasible children.
    \item Fewest remaining constraints, summed across all feasible children.
\end{enumerate}

For the selected variable, the algorithm chooses the child with the fewest remaining fusion constraints.
This continues until all fusion choices are made.
The solver then disables any unresolved in-place choices and uses the partial assignment to complete the solution by deriving the values of all other variables in a second phase.

\paragraph{Completing the solution.}

Once fusion and in-place updates are decided, the solver completes the partial assignment by determining the cluster indices and assigning values to the remaining variables.

Cluster-index variables that resolve through aliasing to the same representative variable will get the same value assigned.
Based on the remaining \texttt{ClusterBefore} constraints, the solver constructs a directed graph of the cluster-index representatives.
Using topological sorting, it assigns values starting from zero to the cluster indices in a way that respects the ordering constraints.
If the graph contains a cycle, the solver cannot complete the current partial assignment and reports infeasibility for this branch.

Once we know all of the cluster indices, the solver can determine the values for the $\pi_{\max}$ variables, which represent the buffer-lifetime boundaries for each buffer to avoid premature overwriting.
The \texttt{ReadAliveThroughWriters} constraints set the lower bounds for these variables, because they require that the max buffer-lifetime index of a buffer must be at least as large as the indices of all clusters that read from it.
For selected in-place reuse paths, the \texttt{InPlaceCluster} constraints set the upper bounds, as they require that the max buffer-lifetime index of a buffer must be less than or equal to the index of the cluster that overwrites it.
For each buffer, the solver chooses the maximum of the lower bounds, as long as it does not exceed any upper bounds.
If it does, the current partial assignment is infeasible.

The iteration direction and fold size variables may have values assigned through constraint propagation.
For any remaining unresolved direction or fold size variable, the solver assigns fallback values: $-1$ for iteration directions and $0$ for the fold sizes.
These assignments are passed to the presolver, which will fail if they contradict any constraints.
If completion of the solution succeeds, the resulting assignment can be evaluated to compute the objective value, which will be used for the optimal solution search.

\paragraph{Searching for an optimal solution.}

For the optimal solution search, the solver branches on the fusion and in-place reuse variables.
The solver remembers the best solution found so far, called the incumbent.
We take the initial solution found by the greedy algorithm as the incumbent, but reopen the choices for fusion and in-place reuse by using the presolved problem.
The idea is that the greedy algorithm may contain suboptimal choices, but provides an upper bound early in the search for the optimal objective value.

The search branches on unresolved in-place variables first, followed by fusion variables.
Within both variable families, the solver starts with the most frequently occurring variable in the remaining constraints.
For each selected variable, both assignments are explored in depth-first order.
Each assignment is then propagated using the presolver, and branches that produce contradictions are discarded.

To avoid exploring branches that cannot improve the incumbent, the solver tries to compute a lower bound on the objective value for the current partial assignment.
Known variables contribute their actual costs, while unresolved binary variables contribute the lower of their possible objective contributions.
The bound is improved using the \texttt{AtMostOneReader} and \texttt{AtMostOneWriter} constraints, which restrict which in-place reuse choices can be enabled together and thus provide a potentially tighter lower bound.
If the lower bound is greater than or equal to the incumbent's cost, the branch is pruned because it cannot produce a better solution.
If we cannot compute a lower bound yet, the search just continues.

When all branching decisions have been made, the solver attempts to complete the assignment as described above.
If it succeeds and the resulting objective value is lower than the incumbent's cost, the incumbent will be updated to the new solution.
Once all branches are either explored or pruned, the solver returns the current incumbent as the best solution found.

Algorithm~\ref{alg:custom-search} displays the simplified version of the search for the optimal solution.
Note, that $\bot$ here denotes an unavailable lower bound, or an infeasible propagation or completion.

\begin{algorithm}[htbp]
    \caption{Custom solver search (simplified).}
    \label{alg:custom-search}
    \begin{algorithmic}[1]
        \Require A partial problem and the best complete solution found so far (the incumbent).
        \Ensure The lowest-cost solution among the incumbent and completions of the problem.
        \Function{Search}{$\mathit{problem}, \mathit{incumbent}$}
            \State $\mathit{bound} \gets \Call{LowerBound}{\mathit{problem}}$
            \If{$\mathit{bound} \neq \bot$ \textbf{and} $\mathit{bound} \geq \Call{Cost}{\mathit{incumbent}}$}
                \State \Return $\mathit{incumbent}$ \Comment{Prune this subtree.}
            \EndIf
            \If{no branching decisions remain in $\mathit{problem}$}
                \State $\mathit{candidate} \gets \Call{CompleteAndEvaluate}{\mathit{problem}}$
                \If{$\mathit{candidate} \neq \bot$ \textbf{and} $\Call{Cost}{\mathit{candidate}} < \Call{Cost}{\mathit{incumbent}}$}
                    \State $\mathit{incumbent} \gets \mathit{candidate}$ \Comment{A better solution was found.}
                \EndIf
                \State \Return $\mathit{incumbent}$
            \EndIf
            \State $\mathit{variable} \gets \Call{ChooseVariable}{\mathit{problem}}$
            \For{$\mathit{value} \in [0,1]$}
                \State $\mathit{child} \gets \Call{AssumeAndPropagate}{\mathit{problem}, \mathit{variable}, \mathit{value}}$
                \If{$\mathit{child} \neq \bot$}

                    \State $\mathit{incumbent} \gets \Call{Search}{\mathit{child}, \mathit{incumbent}}$
                \EndIf
            \EndFor
            \State \Return $\mathit{incumbent}$
        \EndFunction
    \end{algorithmic}
\end{algorithm}

\subsection{Experimental optimizations.}

After the initial implementation of the custom solver, several optimizations were tried to improve its performance.

\paragraph{Default-value assignment.}

The idea of default-value assignments is to detect unresolved binary variables that can be safely fixed to a value without losing an optimal solution.
To implement this, we analyze the requirements from the objective function and the constraints in which a variable occurs.
If these requirements have a common known value, we can safely assign that value to the variable and avoid branching on it.
But if any requirement is unknown, the variable remains unresolved.
This analysis is applied recursively before and during the search.

The current limitation is that the analysis is very conservative.
Tracing the benchmark runs showed that it produced no assignments for the tested instances, although it was invoked during the search.
This is because the requirements are often unknown, and the analysis cannot establish a safe value assignment.
For example, \texttt{ClusterBeforeUnlessFused} requires equal cluster indices when $x_{ij} = 0$ and strict ordering when $x_{ij} = 1$, which means we emit an unknown requirement.
Choosing either value may violate ordering constraints for the current cluster indices, so neither value is safe to assign unconditionally.
Therefore, the analysis cannot assign a default to its unresolved fusion variable.
In the benchmark runs, the optimization worsened the performance of the solver, most likely because of the computational overhead of the analysis.
A more precise analysis could detect more safe assignments in the future, provided that the overhead of the analysis does not outweigh the benefits of reducing the search space.

\paragraph{Direction defaults.}

A similar approach is used for default values of unresolved read and write direction variables.
The implementation groups them by direction-equality relationships and checks if a common value can be assigned safely.
This value must respect already known directions, negativity requirements, and variable bounds.
After assignments, the presolver is used to simplify constraints and the analysis is repeated, as with binary defaults.

Tracing the \texttt{simple} and \texttt{chain} benchmark runs showed that this approach produced assignments, unlike binary defaulting in these runs.
However, the analysis is still conservative and excludes some groups of variables from the assignment, e.g. if they occur in the objective function or in a lowered constraint not covered by the analysis.
Therefore, a more precise analysis could recognize additional safe assignments.

The benchmark also revealed that enabling this optimization makes the performance worse.
A possible explanation would be the analysis overhead, which may outweigh the benefits for the tested instances.
Further profiling is needed to confirm this hypothesis.
A more precise analysis could also increase the computational overhead, so it is not clear if the benefits would outweigh the costs.

\paragraph{Problem decomposition.}

Another optimization is to decompose the problem into multiple independent ones and solve them separately.
The decomposition requires that no constraint couples unresolved variables from different subproblems and that the objective can be split into contributions of the individual subproblems.
If these conditions are met, we can solve them independently and combine their solutions into one for the original problem.
The intended benefit is to reduce the search space by replacing one large search with multiple smaller searches.

However, the current implementation has a few limitations.
It only attempts splitting before the search and does not reapply it during the recursive search.
This could lead to missed opportunities, because the more assignments are known, the easier it could be to recognize independent problems.
The current benchmark also shows that the initial decomposition usually has one dominant problem and a few very small ones, which does not improve the search performance.

The current hypothesis is that just applying it recursively will not provide much benefit unless the branching strategy is adapted to favor choices that find independent problems.
Tracing the benchmark showed that the dominant subproblem contained all remaining fusion and in-place reuse variables that the solver branches on.
One possible idea is to build a dependency graph and find so-called articulation points to guide the branching strategy towards independent subproblems.
Trying to find similarly sized problems could also be beneficial.
All of these ideas need further investigation, but the current implementation can serve as a starting point for future work.
