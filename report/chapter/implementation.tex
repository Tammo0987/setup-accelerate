\section{Implementation}

\subsection{Domain-Specific Constraint Language}

\paragraph{Constraint representation.}

The domain-specific constraint language was designed to represent the constraints of the original ILP formulation as relationships between computations and buffers.
Rather than encoding these relationships directly as integer variables and linear inequalities, the language gives each kind of constraint an explicit constructor.
The language is implemented by the algebraic data type \texttt{Constraint}.
The following code listing shows two examples of constraints that express ordering relationships between computations.

\begin{lstlisting}[language=Haskell]
data Constraint
  = ClusterBefore (Node Comp) (Node Comp)
  | ClusterBeforeUnlessFused (Node Comp) (Node Comp)
  -- Further constraints omitted...
\end{lstlisting}

The order of the computation clusters is represented by integer variables $\pi_i$, where $\pi_i$ denotes the cluster index of the $i$-th computation.
Constraints on these indices ensure that the cluster ordering respects the dependencies between computations, with fused computations sharing the same cluster index.

The constraint \texttt{ClusterBefore} expresses the strict ordering $\pi_i < \pi_j$ between two computations $i$ and $j$.
For dependencies that permit fusion, the constraint \texttt{ClusterBeforeUnlessFused} requires $\pi_i = \pi_j$ if the computations are fused, and $\pi_i < \pi_j$ otherwise.
This constraint makes the relationship between fusion decisions and cluster ordering explicit in the constraint language.

\paragraph{Lowering to ILP.}

To keep support for the external ILP solver, the constraints are lowered into a linear representation.
For each constraint, lowering produces a tuple containing linear constraints, variable bounds and a contribution to the objective.
The lowering signature and its result type are shown in the code listing below:

\begin{lstlisting}[language=Haskell]
lower :: LowerEnv -> Constraint -> Lower

type Lower = State String (LinearConstraint, Bounds, Expression)
\end{lstlisting}

The \texttt{LowerEnv} parameter provides the total number of computations in the problem, which is used for some constraints to generate appropriate bounds and coefficients during lowering.
The \texttt{Lower} type uses a state monad to supply fresh variable names to introduce auxiliary variables when needed.
Some constraints may not produce additional bounds or objective contributions.

For example, the \texttt{HorizontalReadCost} constraint requires auxiliary variables to encode the cost associated with distinct clusters reading the same buffer.
Fresh names ensure that variables introduced for separate constraints do not collide.

As a simple example of the translation, \texttt{ClusterBefore} is lowered to
\[
   \pi_i < \pi_j.
\]

The lowering of \texttt{ClusterBeforeUnlessFused} additionally uses a binary variable $x_{ij}$, where $x_{ij} = 0$ means that computations $i$ and $j$ are fused, and $x_{ij} = 1$ means they are not fused.
The constraint is encoded as:
\[
    x_{ij} \leq \pi_j - \pi_i \leq M \cdot x_{ij},
\]
where $M$ is a sufficiently large constant determined by the total number of computations in the problem.

The function \texttt{lowerAll} lowers all constraints using a shared supply of fresh variable names and combines the results.

\subsection{Presolver}

The constraint language described above allows the problem to be simplified before it is lowered to an ILP.
The presolver uses a substitution to record known variable values and relationships between variables.
It uses this information to derive further assignments, drop already satisfied constraints, and detect contradictions.
These optimizations work directly on the domain-specific constraints, where relationships such as fusion and cluster ordering are still explicit.

\paragraph{Problem representation.}

The presolver represents a problem as a set of unresolved constraints and a substitution.
A substitution contains a mapping of variables to either a constant value or an alias to another variable.
Here is an excerpt of the main types:

\begin{lstlisting}[language=Haskell]
data Value = Const Int | Alias Var

newtype Substitution = Substitution (M.Map Var Value)

data Problem = Problem
  { constraints :: [Constraint]
  , substitution :: Substitution
  }
\end{lstlisting}

When a variable is looked up, the presolver follows the aliases until it resolves to a constant or a representative variable.
The substitution map uses an ordering of the variables to record aliases, which avoids cycles during lookups.

\paragraph{Constraint simplification.}

The main simplification function is:
\begin{lstlisting}[language=Haskell]
instantiate
    :: Substitution
    -> Constraint
    -> Either Infeasible (Maybe Constraint, [Assignment])
\end{lstlisting}

It simplifies a single constraint using the current substitution.
The result either contains the (simplified) constraint --- if it still needs to be enforced --- or omits it if it is already satisfied or represented by new assignments.
An assignment here is a pair of a variable and a value.
If the constraint contradicts the known assignments, it returns \texttt{Infeasible}.

For example, an \texttt{Unfused} constraint directly translates to an assignment of the fusion variable $x_{ij} = 1$.
If $x_{ij} = 0$, the \texttt{ClusterBeforeUnlessFused} constraint establishes $\pi_i = \pi_j$, which is recorded by aliasing the two cluster variables and dropping the constraint.
This also works the other way around: if the cluster variables are already equal, the fusion variable is fixed to $x_{ij} = 0$.
Conversely, if $x_{ij} = 1$, the cluster indices need to be different, which is represented by the emitted \texttt{ClusterBefore} constraint.

Similar rules are used in \texttt{instantiate} to simplify relationships like buffer materialisation, iteration directions, fold sizes, and in-place reuse.
All these rules can trigger further simplifications in other constraints.
This is handled by the \texttt{apply} function, which repeatedly simplifies the constraints until a fixpoint is reached.
This continues until the substitution no longer changes and the assignments in the substitution preserve the information from the dropped constraints.

\paragraph{Graph-based passes.}

The local simplification described above considers only one constraint at a time.
However, some optimization techniques are only possible if we consider multiple constraints together.
Therefore, the presolver also applies passes over the whole problem.
Every pass takes a problem instance and either returns a simplified problem or reports infeasibility.
The type of a pass is defined as follows:

\begin{lstlisting}[language=Haskell]
type Pass = Problem -> Either Infeasible Problem
\end{lstlisting}

The presolver defines several passes, some of which use a graph of the cluster ordering relationships to derive new information.
By default, four of them are enabled:

\begin{itemize}
    \item \texttt{noInPlace} finds buffers marked by \texttt{NoInPlace} constraints and disables the corresponding reuse paths represented by \texttt{InPlaceCluster} constraints.
    \item \texttt{piMaxOrder} derives ordering constraints from selected in-place reuse paths. If all candidate reuse paths associated with another read of the input buffer are disabled, that reader must precede the overwriting writer.
    \item \texttt{orderComponents} identifies strongly connected components in the ordering graph. It either sets the variables within a component equal by adding alias assignments or detects a contradictory cycle and reports infeasibility.
    \item \texttt{orderReachability} uses paths of strict ordering relationships to rule out fusion and in-place reuse choices that require equal cluster indices.
\end{itemize}

For example, \texttt{orderComponents} constructs a directed graph where the vertices are the cluster variables.
A \texttt{ClusterBefore} constraint contributes a strict ($<$) ordering edge.
In comparison, a \texttt{ClusterBeforeUnlessFused} constraint adds a non-strict ($\leq$) ordering edge.

Consider a cycle consisting of three non-strict ordering relationships:
\[
    \pi_i \leq \pi_j, \qquad
    \pi_j \leq \pi_k, \qquad
    \pi_k \leq \pi_i.
\]

Figure~\ref{fig:ordering-cycle} shows the corresponding ordering graph.
\begin{figure}[htbp]
    \centering
    \begin{tikzpicture}[>=stealth, every node/.style={font=\small}]
        \node[draw, circle, minimum size=9mm] (i) at (0, 0) {$\pi_i$};
        \node[draw, circle, minimum size=9mm] (j) at (4, 0) {$\pi_j$};
        \node[draw, circle, minimum size=9mm] (k) at (2, -2) {$\pi_k$};
        \draw[->] (i) -- node[above] {$\leq$} (j);
        \draw[->] (j) -- node[below right] {$\leq$} (k);
        \draw[->] (k) -- node[below left] {$\leq$} (i);
    \end{tikzpicture}
    \caption{A cycle of non-strict ordering relationships forces all three cluster indices to be equal.}
    \label{fig:ordering-cycle}
\end{figure}

Together, these relationships imply that the cluster indices are equal: $\pi_i = \pi_j = \pi_k$.
The pass records this by aliasing the variables in the substitution.
More generally, all variables of a strongly connected component containing only non-strict edges must be equal.
If such a component contains a strict edge, the ordering is contradictory.
For example, if the first relationship were strict ($\pi_i < \pi_j$), the cycle would require $\pi_i < \pi_i$, which is impossible.

The different passes are applied in sequence, followed by the local constraint simplifications.
This will be repeated until a fixpoint is reached, where these simplifications no longer change the problem.
